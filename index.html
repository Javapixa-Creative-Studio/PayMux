Payment gateway configuration is merchant-wide. One notification URL serves everything you build, so the second application forces a choice between coupling your products together or inventing order_id prefix conventions. PayMux takes ownership of the gateway integration instead: your applications talk to PayMux, PayMux talks to Midtrans, and because PayMux opened every transaction it knows exactly who owns each notification.

Idempotency

A retry with the same Idempotency-Key returns the original payment rather than opening a second transaction. Reusing a key with a different body is rejected as a conflict.

Keys are scoped to an environment

A pmx_test_… key works against a sandbox gateway account and pmx_live_… against a production one. PayMux refuses the mismatch rather than letting a test credential move real money.

Amounts

Integers in the currency’s minor unit. For IDR that is one rupiah, so 150000 is Rp 150.000.

Events and delivery

Normalized, signed, and retried until you answer.

PayMux verifies the gateway’s notification, attributes it to its owner, and turns it into one of 23 event types. Every delivery is signed with your destination’s own HMAC-SHA256 secret over <timestamp>.<delivery id>.<raw body>.

Seven attempts, then the delivery is marked dead.

Each delay carries up to ±10% jitter, so a destination coming back online is not hit by every pending delivery at the same instant. A 4xx other than 408, 425 or 429 stops the retries immediately: your endpoint has said the request itself is wrong, and repeating it will not change that.

Money out

A payout has no backstop, so it is off in three places.

Everything above moves money inward, where the worst case of a mistake is a payment that gets refunded through the gateway that took it. A disbursement leaves the merchant balance for an account the caller names, and there is no chargeback on it. A payout happens only when all three of these are true.

Payout simulator the refusals below are PayMux’s real ones
01

The gateway account holds disbursement credentials

Midtrans issues these separately from the payment server key, and only after approving the account for disbursement. PayMux seals them under their own encryption context, so a leak of the payment key is not a leak of this one.

02

The application is permitted to disburse

Off by default, and deliberately the first thing checked: everything else about a payout is irrelevant if the application was never allowed to make one.

03

Somebody approves it

An approver cannot approve their own request — the database refuses it, not a handler. Turn approval off and PayMux insists on a spending limit in its place.

response—
Turn the gates on and request a payout.

Nothing has been sent.

Inbound, sharing a merchant account is harmless: application A cannot take application B’s money. Outbound, every application with an API key spends from the same balance. Without limits, one leaked API key drains what every other application collected. README — Why the per-application limit is not optional

The daily limit counts payouts still in flight, including ones whose outcome is unknown, because money the gateway already has cannot be spent twice. A payout also names a beneficiary, never a raw account number: a destination is reviewed once and reused, so a typo cannot send money to a stranger.

The state that matters

StatusMeans
REQUESTEDWaiting on a person. Nothing sent.
APPROVEDReleased, queued. Still nothing sent.
SUBMITTEDThe gateway has it. PayMux can no longer stop it.
UNRESOLVEDSent, and PayMux cannot tell what happened. Never re-issue one of these: a new payout carries a new idempotency key, and the gateway would treat it as a second instruction. PayMux resolves it by re-sending under the original key.
COMPLETEDThe beneficiary was paid.
FAILEDIt did not happen; the funds stayed put.
REJECTEDRefused before anything was attempted.

There is deliberately no event for a payout whose outcome PayMux cannot determine. That state says something about PayMux rather than about the payout. Applications hear from us when there is an answer.

Gateway-specific options are namespaced and validated

Common parameters are normalized. Anything Midtrans-specific goes in a gateway_options.midtrans block, and unknown fields are rejected rather than forwarded: PayMux never passes an unvalidated blob to a payment gateway under your merchant credentials.

The metric worth paging on

paymux_payouts_total{status="UNRESOLVED"} above zero means money may have moved without PayMux knowing. Labels across all eleven metric families are deliberately coarse — route patterns rather than paths, status classes rather than codes — because a payment identifier in a label would make the series unbounded.

Inside

Two Go binaries and a database.

No broker, no cache, no queue service. The delivery queue is a table, and the worker leases from it. Gateway-specific code lives only in the adapter, which is what makes a second gateway a matter of writing an adapter rather than rewriting the core.

What secrets are done with

Gateway server keys and webhook secrets are sealed with AES-256-GCM. API keys are stored as SHA-256 hashes and the plaintext is shown once, at creation. Administrator passwords use Argon2id. PayMux never stores card numbers, CVVs or any raw card credential.

Outbound destinations are checked twice

Webhook destinations are blocked from private, loopback, link-local and cloud-metadata ranges, and checked again at connection time, so a hostname cannot change its answer between validation and delivery.

Inbound callbacks are verified first

Midtrans notifications are verified against the documented signature before anything is applied to a payment.

Status

What is not proven yet.

Disbursement has never reached a real gateway

It is implemented end to end, and every path to the gateway has been exercised — but only against refused placeholder credentials, because Midtrans gates Iris behind separate merchant approval. Real sandbox keys are the only way to confirm the final hop.

Everything on the inbound side — payments, refunds, subscriptions, notifications, events and delivery — runs against the Midtrans sandbox, and the integration tests exercise the whole path: three applications sharing one gateway account, a payment taken by one of them, and the signed event reaching only its owner.

One gateway today

PayMux is Midtrans-first and its architecture is gateway-agnostic. The long-term goal is one integration for applications and several payment gateways behind it. Nothing on this page claims a gateway that is not in the repository.

Before it handles a real transaction

PayMux serves plain HTTP and expects TLS termination in front of it. Read docs/production.md first: it covers the encryption key’s recovery characteristics (there are none), the settings whose defaults are wrong for production, backups, what to alert on, and what PayMux deliberately does not do.

Get PayMux

Two binaries, a database, and your own gateway keys.

PayMux is self-hosted: you run it, you hold the keys, and nothing about your merchant account passes through anyone else. Requirements are Docker, or Go 1.25+ and PostgreSQL 15+.

installbash
git clone https://github.com/Javapixa-Creative-Studio/PayMux.git
cd PayMux
cp .env.example .env

# generate the key that seals every gateway credential
openssl rand -hex 32

docker compose up -d
Then connect your gateway

Add your Midtrans merchant ID, client key and server key in the dashboard, and press Test connection. PayMux asks the gateway for a transaction that cannot exist: an answer of “no such transaction” proves the credentials were accepted, and nothing is left behind in your merchant account. Create an application, an API key and a webhook destination, then point the gateway’s Payment Notification URL at /webhooks/midtrans on your deployment.

Two storefronts to prove it

The repository ships a demo profile with two independent shops that collect into one merchant account and cannot see each other’s orders. It is the claim on this page, running, in about a minute. Setup is in examples/README.md.
